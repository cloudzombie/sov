## FINDING 1 — the sfo3 relay is running a pre-0.2.6 binary, and bit 3 is the hazard

`sov_getDeployments` on sfo3 returns **only three** deployments. But `mainnet_deployments()`
(`chain/crates/rpc/src/daemon.rs:1221`) has carried a **fourth** since v0.2.6 — `tx-timestamp`,
bit 3, `MAINNET_TX_TIMESTAMP_START_HEIGHT` = 17280, min-activation `start + 288` = 17568, timeout
`start + 3*288` = 18144, 288-block window, 9/10, `lockinontimeout = false`. A v0.2.6+ node cannot
omit it. **sfo3 is therefore serving mainnet on a binary older than v0.2.6.**

**Both** droplets in fact run the **identical** binary — `sha256 2969de29…` on sfo3 and fra1 alike
— so the entire cloud fleet is pre-0.2.6, not just the one relay. They mine
(`"mine": true` in both node-configs) and emit `version_bits = 7` (`0b111`). The v0.2.6+ miner
(proposer `182ade36…`, ~87% of recent blocks) emits `15` (`0b1111`), the v0.2.6 `signal_mask`
(`daemon.rs:1297`).

### The signaling arithmetic — counted, not assumed

An early 6-block spot check read `15` every time and suggested ~100% signaling. **That was an
unlucky sample and it was wrong.** Counting every block in each 288-block window
(`is_met` is `signaling * den >= num * period`, so 9/10 of 288 needs **≥260**):

| window | bit-3 blocks / 288 | ≥260? |
|---|---|---|
| `[17280, 17568)` | well short (~54% of a partial sample) | no |
| `[17568, 17856)` | **239** | no — fails |
| `[17856, 18144)` | **260** | **yes — by exactly one block** |

The last window met the threshold *exactly*: 260 × 10 = 2600 ≥ 9 × 288 = 2592. At 259 it would
have failed.

### Why it locked in rather than timing out

The timeout height is **18144** — the same boundary that closed the winning window, so the
ordering inside `next_state()` decides the outcome. Read at
`chain/crates/governance/src/lib.rs:459`: in the `Started` arm the **threshold check runs first**,
and only if it is unmet does the timeout check run. So at 18144 the deployment went
**LockedIn**, not `Failed`. Next boundary, 18432, `LockedIn → Active` (min-activation 17568 long
passed).

**CONFIRMED: `tx-timestamp` (bit 3) went ACTIVE at height 18432**, roughly 2026-08-05. Tip today
is 18716 — it has been live for ~280 blocks.

### The hazard, now current rather than hypothetical

Every v0.2.6+ node has bit 3 Active. **Both droplets are pre-0.2.6 and do not know the deployment
exists**, so they would reject an `Action::Timestamped` transaction — and therefore **reject any
block containing one**. That is a chain split, and the fleet is on the losing side of it.

### How exposed are we actually? Less than it first looks

`Timestamped` is an **opt-in outermost envelope**, one variant of `Action`
(`Timestamped { created_at_ms, inner: Box<Action> }`), exactly like `Tipped`. It is NOT applied to
every transaction — a tx carries it only if the sender deliberately wraps the action
(`transaction.rs:427`: *"This is the OUTERMOST carrier… may never appear below the top level"*).
The SDK's receipt type says the same from the other side: `timing` is *"omitted entirely when the
transaction did not use the `Timestamped` envelope — which is why an ordinary receipt's JSON is
byte-for-byte what it was before this field existed."*

**And no client can construct one.** `Action::Timestamped` appears only in consensus types,
weight, receipt, gas, execution, blockchain, governance, the daemon preset, and tests. There is no
construction site in the Rust wallet, in Station (`node/src`), or in the TS SDK — the SDK only
*reads* `timing` off receipts. The deployment is Active on-chain with **no client that emits it**.

Confirmed on-chain: both droplets report tip **18721**, identical (no divergence), and sampled
blocks 18700–18721 carry **0 transactions**.

So the split needs someone to deliberately write new code to build the envelope. It is a live
consensus hazard worth closing, but it is genuinely dormant — not one stray click away. Fix it on
a working upgrade path; do not risk the last relay to rush it.

**Process point:** bit 3 was armed in v0.2.6 on 2026-07-30 and its entire signaling window
(17280 → 18144) opened and closed without a fleet upgrade or a single note recording that an
activation was in flight. Bits 0/1/2 each got a runbook; bit 3 got none.

## FINDING 4 — v0.2.10 CANNOT START on a 2 GB node (upgrade attempted and rolled back)

Attempted the sfo3 upgrade on 2026-08-06 with the checksum-verified CI artifact
(`SOV-Node-v0.2.10-linux-x64.tar.gz`, `sha256 340e5858…`). **It OOM-killed on every start and was
rolled back.**

- Died ~21 s into startup, **before emitting a single log line**. The old binary logs
  `chain 'sov-mainnet' — resumed 18800 block(s)` within ~2 s. systemd recorded peaks of
  483 M / 918 M / 1.4 G across successive restarts; `Failed with result 'oom-kill'`, then a
  restart loop (counter reached 5) with the **public RPC down**.
- **This is not the RandomX dataset and not the v0.2.9 light-mode guard.** The guard worked
  correctly — `MemAvailable` after stop was 1.65 GB, under the 2.6 GB
  `FAST_DATASET_MIN_AVAIL_BYTES`, so it demoted to light. The process never reached mining. The
  cost is in the **startup chain-replay path**, most plausibly v0.2.7's `BlockImporter`/verifier
  rework.
- Rolled back to `sov-rpcd.bak.pre0210` (`sha256 2969de29…`). sfo3 is stable again: RSS flat at
  **898 MB**, `MemAvailable` ~820 MB, 0 restarts, mining, RPC serving. The failed binary is kept
  at `/usr/local/bin/sov-rpcd.v0210.failed` for diagnosis.
- **fra1 was deliberately NOT attempted.** It would hit a *different* failure: after a stop it
  sees ~3.5 GB available, which is ABOVE the 2.6 GB threshold, so v0.2.10 selects **fast** mode
  and allocates the 2 GB dataset on top of the higher startup baseline — on a 4 GB box already
  running at 3.4 GB RSS with no swap.

**This is a real regression well beyond this fleet: no 2 GB node can currently run current SOV.**
That is a fresh-node accessibility problem, and it should be reproduced and fixed in code — the
memory ceiling wants a bounded startup replay, not a bigger droplet.

Neither box has swap (`SwapTotal: 0`) despite 45+ GB free disk, which is why a transient startup
spike is an outright kill rather than a slow patch.
