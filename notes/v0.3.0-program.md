# v0.3.0 PROGRAM — UTXO LEDGER (research + design; NOTHING here is shipped)

**Mission**: v0.3.0's headline is moving SOV's value ledger from the account/nonce
model to a UTXO model. This document makes that decision *executable*: it designs
the full migration honestly, designs a **hybrid ledger** (accounts + a first-class
UTXO layer coexisting permanently) at the same depth as a competing option per the
owner's directive ("how to have UTXO WITH our account model"), prices the
lower-cost mempool-policy alternatives fairly, and states one recommendation with
the reasoning in the open. Every claim below is either pinned to a file:line in
this tree, cited to named external prior art with a confidence level, or listed as
an OPEN MEASUREMENT. Nothing is estimated where we have not measured.

**Owner directives (LAW, inherited verbatim from the v0.2.0 program):**
- SOLID AS GRANITE. NO MISTAKES, NO FAKE ANYTHING.
- No fuzzy logic: consensus paths use exact arithmetic, exact state machines,
  pinned KATs.
- No made-up nothings: every claim is proven by a test/bench in the tree or it is
  not claimed.
- Genesis `cb0272ff88e64c18cde0257f7fae1c8236b02651f10cc7a02456fd682ee2e72d` is
  FROZEN. Every slice proves byte-identity (genesis pin + KAT) before merge.
- Everything ships DORMANT behind a BIP-9 deployment; activation is a separate,
  explicitly-approved event after external audit (law F7, the Upgrade Playbook).
- Law **F8** (safe-exit / nothing-ever-stranded) binds this program harder than
  any before it — a ledger-model migration is the largest stranding risk this
  chain will ever face. §5 is written to survive an adversarial audit.

## 0. GROUND TRUTH — what the code is today (all claims pinned)

The whole design stands on these verified facts; if any is wrong, the design must
be re-derived.

**The ledger is an account map plus escrow scalars.**
`chain/crates/state/src/account.rs:29-48`:
`Account { nonce: u64, balance, locked, unlock_height, key: Option<PublicKey>, code: Option<Vec<u8>> }`.
The module doc says it outright: *"SOV is an account-based chain (like
Ethereum/NEAR, unlike Bitcoin's UTXOs)."* The `Ledger`
(`chain/crates/state/src/ledger.rs:288-377`) holds ~20 fields; **14 are keyed on
`AccountId` or embed one** (accounts, contract storage, token balances, token
velocity windows, NFT/SNS ownership, multisig policies + proposals, vaults, HTLC
locker/recipient). Supply (`ledger.rs:972-984`) =
Σ(balance+locked) over accounts **+ `shielded_value` + `htlc_locked` +
`vault_collateral`** — three escrow buckets already live *outside* accounts.

**The nonce is load-bearing in five distinct places:**
1. STF strict equality — `chain/crates/runtime/src/execution.rs:221-226`:
   `if tx.nonce != signer.nonce { return Err(BadNonce{..}) }`; consumed even when
   the action fails (`:302-306`).
2. Mempool gap-free admission — `chain/crates/mempool/src/lib.rs:420-435`: a tx
   whose nonce exceeds `on_chain + pooled_run` is **rejected**, not queued
   (`MempoolError::NonceGap`). There is no Ethereum-style "future/queued" tier.
3. The multisig approval preimage `multisig_signing_bytes(account, nonce, action)`
   — `chain/crates/types/src/transaction.rs:449-464` (SHIPPED, frozen).
4. The key-rotation possession proof `rotation_signing_bytes(signer, nonce,
   new_key)` — `transaction.rs:472-486` (SHIPPED, frozen).
5. The deterministic multisig `proposal_id` embeds proposer nonce —
   `execution.rs:1723-1740` (SHIPPED, frozen).
Plus one **still-changeable** sixth: pool-v2's pinned decision **D4** binds the
ML-DSA-65 carrier auth to `{tx signer, nonce}` — but the code does NOT yet
implement that binding (`chain/crates/shielded-pq/src/bundle.rs:82-83` and `:116`
are explicit W2 TODOs). See §10 DECISION-NOW.

**Head-of-line blocking is total.** Selection
(`mempool/src/lib.rs:700-741`) walks each signer's contiguous nonce run and stops
at the first hole; nothing above a hole is ever proposed
(test `select_never_proposes_a_gap_tx`, `lib.rs:1252`). One stuck tx freezes the
sender's entire pipeline. This is the single strongest functional argument for a
UTXO layer.

**The per-sender cap is 256 by default** — `default_per_sender(capacity) =
(capacity/64).max(16)` (`lib.rs:185-192`) with `default_mempool_capacity() =
16_384` (`chain/crates/rpc/src/daemon.rs:377-379`). For calibration: Bitcoin Core
historically allowed only **25** chained unconfirmed ancestors/descendants
(101 kvB each), and Core 31.0 replaced that with **cluster limits of 64 tx /
101 kvB**; TRUC (BIP-431) transactions are limited to **one** unconfirmed parent
and **one** child. SOV's current allowance is already 4–10× more permissive than
Bitcoin's. (External facts, high confidence: Bitcoin Core
`doc/policy/mempool-limits.md`; Core 31.0 release notes; BIP-431.)

**The fee market already exists and is node-local.** Tips ride
`Action::Tipped { tip, inner }` (tag 30, `transaction.rs:357-370`); consensus
enforces only conservation (tip is a pure signer→miner transfer,
`execution.rs:1553-1561`; `distribute_fee` credits everything to the miner,
nothing burned, `:1652-1659`). The dynamic floor, RBF (`MIN_RBF_BUMP_GRAINS =
1_000`, `lib.rs:183`), eviction, and "low-fee WAITS" are all mempool policy with
zero consensus surface (`lib.rs:332-363, 527-553`). **A ledger-model change
leaves the auction almost intact** — only the nonce-package grouping in `select`
must become dependency-graph/ancestor-package selection.

**Signatures are hybrid and BIG.** `PublicKey::V2HybridMlDsa65` = 32 + 1952 B;
`Signature::V2HybridMlDsa65` = 64 + 3309 = 3373 B; verification is a strict
conjunction of Ed25519 AND ML-DSA-65 (`chain/crates/crypto/src/keys.rs:127-149`).
**A hybrid signing envelope is ~5.3 KB.** This single number shapes the whole
UTXO design: Bitcoin-style one-signature-per-input is unaffordable; the design
must sign once per key per transaction (§2.4).

**Implicit account ids are already pay-to-key-hash.**
`implicit_account_id() = hex(blake3(borsh(PublicKey)))`
(`crypto/src/keys.rs:114-119`) — over the scheme byte and BOTH key halves. An
implicit id is exactly what Bitcoin calls a P2PKH address: a 32-byte hash
commitment to a key, spendable only by revealing the preimage key and signing.
The UTXO lock design in §2.3 reuses this unchanged.

**The shielded pools are already UTXO ledgers.**
`ShieldedState { tree, anchors, nullifiers, commitments }`
(`chain/crates/shielded/src/state.rs:35-49`) — notes are outputs, nullifiers are
the spent-set, notes are independent and unordered. The only account coupling is
one line of boundary code: the transparent leg debits/credits `tx.signer`'s
balance by the bundle's signed value balance (`execution.rs:577-658`). The
turnstile (`shielded_value` with `checked_sub`, can never go negative,
`ledger.rs:1015-1031`) and the drain limiter (576-block window, 21,000 XUS,
`chain/crates/mining/src/lib.rs:175-181`) are consensus-enforced and
proof-system-independent. **SOV already runs a hybrid ledger.** The honest
question of this program is not "can SOV have UTXO" but "should the UTXO layer
be transparent, first-class, and general-purpose alongside accounts" (§6).

**State commitment**: depth-256 sparse Merkle tree over Borsh leaves at
domain-tagged blake3 slots (`ledger.rs:384-487`; tags 0x01–0x07 taken, account
slots untagged). All feature sub-states are **absent-when-empty**, which is how
every feature since launch was added without moving frozen genesis. Six
sub-states (HTLCs, NFT classes, NFTs, multisig, proposals, vaults) are committed
as whole-map digests — O(n) recommit per write (known wart).

**Reorg machinery**: per-write pre-image undo journal (`UndoOp`, 20 variants,
`ledger.rs:236-263`), `REORG_UNDO_WINDOW = 256` (`blockchain.rs:484`). Reorgs
within 256 blocks are O(depth); deeper falls back to O(chain-length) replay
(`rebuild_branch`, `blockchain.rs:2294-2360`).

**Activation machinery** (the migration vehicle): BIP-9 with 90%/288 thresholds,
bits 0 (tx-domain) and 1 (fee-auction) ACTIVE on mainnet since h11520; bit 2
reserved for shielded-v2; **bits 3..28 free** (law F1). Baked, chain-id-keyed
presets (`baked_deployments()`, `daemon.rs:932-1004`); the F6 boot-order
invariant has a single constructor `genesis_chain_with_baked_preset`
(`daemon.rs:1022-1032`) called by all three replay tiers. The `TxDomainMode
{ Legacy, Grace, Bound }` resolver (`blockchain.rs:874-895`) is the proven
template for any multi-phase transition. NOTE for this program: F6's second half
("a test greps/asserts no bare construction bypasses it") is **documented but not
mechanically enforced** today — `Blockchain::new` is called bare in ~24 places
(tests, redteam, `node/src/main.rs:52`, `sov-miner.rs:126`). v0.3.0 must close
that gap regardless of which option wins (§10, W-F6).

**Size of the blast zone**: `chain/crates/` = **57,183 lines of Rust**;
`execution.rs` 6,463; `blockchain.rs` 5,056; `ledger.rs` 2,569; mempool 1,746;
**31 Action variants** (tags 0–30, order consensus-frozen); **814 tests**
repo-wide; a TS SDK second client (`sdk/`) with byte-pinned KAT parity; Station
GUI 10,375 lines with the nonce as user-visible UI copy (`node/src/gui.rs:1963-2015`);
45 RPC methods under law F5 (additive-only).

## 1. THE CASE, STATED FAIRLY

### 1.1 What UTXO buys SOV — concretely

1. **Independent transaction ordering.** Today one account's transactions form a
   strict chain: STF `tx.nonce != signer.nonce ⇒ BadNonce`
   (`execution.rs:221-226`), mempool refuses gaps at admission
   (`lib.rs:420-435`), and selection stops at the first hole (`lib.rs:714-717`).
   A UTXO transaction depends only on its named inputs; unrelated spends by the
   same owner are orderable in any sequence and can never block each other. This
   is the one property NO mempool-policy change can deliver (§7.1) — it is
   inherent to the nonce STF rule.
2. **Exact, trivial affordability.** Today admission-time affordability is
   approximate bookkeeping (`base_outflow`/`pending_outflow`, `lib.rs:152-162,
   380-386`) with a re-eviction sweep after every block (`prune`,
   `lib.rs:591-610`) — and the file's own doc comment about it is stale. Under
   UTXO an input either exists unspent or it does not; double-spend conflict is
   set-membership.
3. **Parallel validation — with an honest caveat.** UTXO validation is
   embarrassingly parallel in principle (disjoint input sets commute). BUT: on
   SOV the dominant per-tx cost is the hybrid ML-DSA-65 + Ed25519 verify, which
   is **already stateless and parallelizable today** without any ledger change —
   the sequential part is state application, which is cheap map writes. How much
   wall-clock a parallel apply would actually save is an OPEN MEASUREMENT (§12);
   we do not claim a number.
4. **Better privacy defaults.** Account ids are stable, reused, and public;
   every payment to/from `81f4ccaa…` links. UTXO wallets derive a fresh lock per
   output (HD chains already exist: BIP-39/SLIP-0010, `wallet/src/hd.rs`), so
   passive linkage requires clustering heuristics rather than being free. This is
   a *default*, not shielding — the shielded pools remain the privacy layer.
5. **Cheaper conceptual reorg handling.** Reorg-orphaned UTXO txs re-enter the
   pool valid-by-construction unless their inputs were spent on the new branch;
   account txs can strand behind re-ordered nonces (the mempool grew
   `evict_stranded`, `STRANDED_TTL_MS = 30 min`, `lib.rs:49, 621-653`, precisely
   for this). Note the undo-journal reorg cost itself (O(depth) ≤ 256) is
   already good and a UTXO set neither helps nor hurts it much — the win is in
   *transaction survivability*, not in rollback cost.
6. **Receiver-side coin control** — a reserve-asset property: a treasury can
   hold value as many independently-keyed outputs (cold, multisig, timelocked in
   tranches) instead of one hot account row, and can prove reserves by opening
   selected outputs. Accounts can approximate this only by key-splitting into
   many accounts.

### 1.2 What it costs — concretely

1. **The five frozen nonce bindings** (§0). Two of them
   (`multisig_signing_bytes`, `rotation_signing_bytes`) are shipped consensus
   preimages that cannot change without a fork of their own.
2. **Everything account-keyed** (§4): 14 of 20 ledger fields, xUSD vaults,
   multisig policies, compliance velocity windows, name resolution, contract
   identity ("contract == account with code", `execution.rs:461`).
3. **KAT + second-client blast radius**: `state.json`, `stf.json`, and (if the
   envelope changes) `transactions.json` all regenerate; the TS SDK
   (`sdk/src/{borsh,state,stf,smt,verify}.ts`) must move in lockstep or the
   second-client guarantee (SECOND-CLIENT.md) is void.
4. **The 5.3 KB hybrid envelope** taxes every input-bearing design (§2.4).
5. **Dual execution engines forever** for full migration (§3.4) — the cost most
   easily underpriced, so it gets its own section.
6. **Audit surface**: the v0.2.0 program already queues an external audit; a
   ledger migration multiplies the surface that must clear it.

### 1.3 What SOV already has that Bitcoin-envy misreads

Stated plainly because an honest decision needs it: SOV's fee market is already
Bitcoin-shaped (tips, RBF with a BIP-125-style bump floor, dynamic eviction
floor, low-fee-waits), and SOV's per-sender allowance (256) is *more* permissive
than Bitcoin's was (25) or is (64-tx clusters). The gap to Bitcoin is **not** the
fee market. It is (a) nonce head-of-line blocking, (b) bearer-instrument outputs
with per-output keys, (c) parallel-validation potential. The options in §2/§6/§7
are scored against those three, not against a fee market we already have.

## 2. OPTION A — FULL MIGRATION: the model design

### 2.1 Which UTXO model — the pivotal decision

Candidates researched:

- **Bitcoin pure UTXO** (value + script lock, no state). Battle-tested gold
  standard for bearer value. But it has NO expression for evolving named state:
  no CDP vault (collateral+debt mutating under an oracle price), no persistent
  multisig *policy* (Bitcoin multisig is per-output, forever fixed at output
  creation), no name registry with resolver updates, no compliance velocity
  windows, no contract storage. Adopting it verbatim deletes those features.
- **Cardano eUTXO** (Chakravarty, Chapman, MacKenzie, Melkonian, Peyton Jones,
  Wadler — "The Extended UTXO Model", WTSC/FC 2020; high confidence). Outputs
  carry a **datum** (arbitrary data) and are locked by a **validator** script
  taking (datum, redeemer, tx context). State machines thread through the chain
  as a chain of outputs. Deterministic validation (fees knowable pre-submission)
  is a real virtue. Known structural costs: **contention on shared state** — a
  state-thread is ONE output, so concurrent users race to spend it (the famous
  Cardano DEX concurrency problem; SOV's oracle price and per-asset compliance
  policies are exactly such global datums; Cardano later added reference
  inputs/CIP-31 to let txs *read* a datum without consuming it — medium-high
  confidence).
- **Ergo** (eUTXO with registers + ErgoScript/Sigma protocols, storage rent;
  medium confidence on details): proves eUTXO can run without an account layer,
  at the cost of every dApp managing state-thread contention itself.
- **Nervos CKB cell model** (generalized UTXO: cells with capacity + data, lock
  script = ownership, type script = state-transition validation; high confidence
  from Nervos docs/RFC-0002): the cleanest general framework, and the honest
  proof that "UTXO with rich state" means shipping a script VM in consensus.
- **Zcash note model**: what SOV's pools already are (§0).

**Determination**: if v0.3.0 is a FULL migration (accounts deleted), pure
Bitcoin UTXO is not on the table — it cannot express xUSD, and xUSD is on the
roadmap as core to the mission. The only honest full-migration target is an
**eUTXO with typed datums** — but NOT a general script VM. SOV's reserve-grade
bar ("no unproven crypto/VM in the trust path") argues for **typed locks**: a
closed Rust enum of validation rules, exactly like today's Action dispatch,
rather than an interpreter evaluating user scripts in consensus. Call this
**eUTXO-T** (typed): the expressiveness of datums, the auditability of a closed
enum, no new VM in the trust path.

### 2.2 Output and outpoint format (eUTXO-T)

```rust
/// One unspent output. Borsh; committed at SMT slot blake3(0x08 ‖ outpoint).
pub struct Output {
    pub value: Balance,          // XUS grains
    pub lock: Lock,              // who/what can spend
    pub datum: Option<Vec<u8>>,  // typed per-Lock payload; None for plain value
}
pub struct Outpoint { pub txid: Hash, pub vout: u32 }
```

`Lock` is the closed enum (initial set, each variant = one audited validation
arm, mirroring today's Action arms):

```rust
pub enum Lock {
    /// Pay-to-key-hash: 32-byte blake3(borsh(PublicKey)) — IDENTICAL derivation
    /// to today's implicit account id (keys.rs:114). Witness: full PublicKey
    /// (hash must match) + hybrid signature over the tx sighash.
    Key([u8; 32]),
    /// M-of-N over key hashes, fixed at output creation (Bitcoin-style).
    MultiKey { threshold: u16, key_hashes: Vec<[u8; 32]> },
    /// Key + not-spendable-before height (vesting / timelock tranches).
    KeyAfter { key_hash: [u8; 32], height: u64 },
    /// HTLC: claimant on preimage before timeout, refund key after.
    Htlc { hashlock: Hash, claim_key: [u8; 32], refund_key: [u8; 32], timeout_height: u64 },
    /// State-thread head for a typed subsystem (vault, name, token, policy…).
    /// `kind` selects the consensus transition rules; datum carries the state.
    Thread { kind: ThreadKind, controller: [u8; 32] },
}
```

The UTXO set commits into the existing SMT under a new tag byte `0x08`
(0x01–0x07 are taken, `ledger.rs:384-487`), absent-when-empty — the pre-existing
state root is untouched until the first output exists, preserving frozen genesis
byte-for-byte (the same trick every feature since launch used).

### 2.3 Transaction format

```rust
pub struct UtxoTransaction {
    pub inputs: Vec<Input>,      // Input { outpoint, key_index: u16 }
    pub outputs: Vec<Output>,
    pub locktime: u64,           // not valid before this height; 0 = none
}
pub struct UtxoWitnessSet {
    /// One entry per DISTINCT key used across all inputs; inputs reference by
    /// key_index. This is the 5.3 KB tax answer: a wallet spending 20 of its
    /// own outputs signs ONCE, not 20 times.
    pub keys: Vec<PublicKey>,
    pub signatures: Vec<Signature>,   // parallel to keys
    pub preimages: Vec<Vec<u8>>,      // HTLC reveals, indexed from Input
}
pub struct SignedUtxoTransaction { pub tx: UtxoTransaction, pub witness: UtxoWitnessSet }
```

- `txid = Hash::digest(borsh(UtxoTransaction))` — witness EXCLUDED, so ids are
  non-malleable by construction (SegWit's lesson, adopted from birth; today's
  account tx id already hashes the unsigned body, `transaction.rs:531`, so this
  is continuity, not novelty).
- Fee = `Σ input values − Σ output values`, must be ≥ the intrinsic weight fee
  (§2.5). No fee field; nothing burned (preserving `distribute_fee`'s law).
  Fees are claimed by the coinbase, Bitcoin-style, which also removes today's
  per-tx write to the miner's account — the one write that serializes every tx.

### 2.4 Sighash — hybrid, non-negotiable, chain-bound from birth

The signature scheme stays **hybrid Ed25519 + ML-DSA-65 in strict conjunction**
(`keys.rs:127-149`) — this is SOV's core claim and is not touched. The sighash:

```
preimage = "sov:utxo-tx:v1" ‖ 0x00 ‖ chain_id ‖ 0x00 ‖ genesis(32)
           ‖ blake3(borsh(all input outpoints))
           ‖ blake3(borsh(all input VALUES))        // BIP-341 lesson: sign the
           ‖ blake3(borsh(all outputs))             // amounts so air-gapped
           ‖ le64(locktime)                         // signers can't be lied to
```

- Domain framing reuses `SigningDomain::frame` byte-for-byte
  (`primitives/src/signing_domain.rs:66-79`). UTXO txs are **Bound-only from
  birth** — there is no Legacy/Grace ladder to inherit because no pre-fork UTXO
  tx exists. Cross-network replay is dead on arrival.
- ONE sighash per transaction (no SIGHASH_SINGLE/ANYONECANPAY menu in v1 —
  every historical Bitcoin sighash CVE lived in that menu; add modes later as a
  versioned extension if coinjoin-style protocols need them).
- Signing input values closes the offline-signer lie (external fact, high
  confidence: this is why BIP-143/BIP-341 commit to amounts).

### 2.5 Fees and the blockspace auction under eUTXO-T

- Intrinsic floor: keep the frozen gas schedule as a **weight formula** —
  `min_fee = (INTRINSIC_GAS + per-input/per-output/per-datum-byte gas) ×
  gas_price(10 grains)` — same constants discipline as `gas.rs` (frozen,
  consensus-critical).
- The auction: `effective_feerate = (Σin − Σout) / weight`. Mempool ordering,
  eviction floor, and RBF port with one substitution: the conflict unit changes
  from `(signer, nonce)` slot to **input-set intersection** (BIP-125 style), and
  the RBF bump floor stays `MIN_RBF_BUMP_GRAINS`-per-weight shaped.
- Per-sender cap → **cluster limits**: "sender" stops being the scarcity unit;
  adopt Bitcoin Core 31's shape (bounded connected components in the in-pool
  dependency graph; Core's numbers are 64 tx / 101 kvB — ours must be sized
  against OUR block weight, an OPEN MEASUREMENT, not copied blind).
- Package selection: `select()`'s per-signer nonce packages become ancestor-set
  packages; the "package held to its cheap head's bid" comment in
  `lib.rs` already describes ancestor-feerate — the concept ports directly.

### 2.6 Where full migration bleeds: the stateful subsystems

Every account-keyed subsystem must become a Thread output or die (full table in
§4). Three are structurally painful and the pain is inherent, not incidental:

1. **Oracle + compliance policies are GLOBAL state.** An eUTXO thread is one
   output; every vault touch and every policed token transfer would contend on
   the oracle-price/policy thread (Cardano's concurrency problem, verbatim).
   The fix (reference-inputs à la CIP-31 — read without consuming) is another
   consensus mechanism to design, implement, and audit.
2. **Compliance velocity windows are per-(asset, holder) rolling state** —
   identity-keyed by definition. There is no natural UTXO expression; options
   are (a) drop the feature, (b) keep an identity sidecar (= a mini account
   model surviving inside the "full" migration — at which point §6 is honest
   about it and this option is not), (c) per-output windows, which change the
   feature's meaning (a holder splits outputs to reset windows).
3. **Contracts**: "contract == account with code + account-keyed storage"
   (`execution.rs:461-489`, `contract_storage`). eUTXO-T without a script VM
   cannot host them; a CKB-style consensus VM violates the reserve-grade bar
   this year. Honest options: freeze contracts (only test deployments exist —
   verified, no mainnet contract usage found) or keep a contract sidecar
   (again: a partial account model survives).

The pattern in all three is the same and the document does not hide it: **a
"full" migration that preserves SOV's roadmap converges back toward a hybrid.**
That observation, not preference, is what drives the recommendation in §9.

## 3. OPTION A — MIGRATION MECHANICS AT HEIGHT H

Written for full migration; §6's hybrid needs NONE of this section (its §6.5).

### 3.1 The conversion

At activation height `H_a` (BIP-9, bit 3, LOT=false, thresholds per F1 house
style), every node performs one deterministic state transformation as part of
connecting block `H_a` — not a new block type, not an admin tx, not an airdrop
file: pure STF, identically computed by every node from its own state at
`H_a − 1`:

- For each `Account` in `BTreeMap` iteration order (already deterministic):
  - `balance > 0` → one `Output { value: balance, lock }`:
    - keyed account → `Lock::Key(blake3(borsh(key)))`;
    - implicit keyless → `Lock::Key(hex-decoded id)` (the id IS the key hash);
    - **named keyless → `Lock::Thread{ kind: NamedClaim, .. }` with the name in
      the datum**, spendable by the same claim rule that `RotateKey` enforces
      today — see §5.3, this is the hardest F8 case;
  - `locked > 0` (vesting) → `Output` with `Lock::KeyAfter { key_hash,
    height: unlock_height }`;
  - contract accounts / vaults / multisig policies / token balances / NFTs →
    per-subsystem rules in §4 (each becomes a Thread output or a retained
    sidecar).
- Deterministic minting order ⇒ deterministic synthetic outpoints:
  `txid = blake3("sov:utxo-genesis:v1" ‖ 0x00 ‖ account_id)`, `vout` by rule.
  Every wallet can compute its own outpoints offline from the rule alone.

### 3.2 What commits to the conversion, and how every node verifies it

The conversion is committed by **the state root of block `H_a` itself** — the
SMT gains the 0x08-tagged UTXO leaves and drops the account leaves, and
`header.state_root` must match on every node (`try_connect_block`,
`blockchain.rs:1711-1734`, already enforces `StateRootMismatch`). No side
channel, no snapshot file, no trusted party: a node that computes a different
conversion computes a different root and rejects/gets-rejected — loudly, at the
boundary, not silently later. Additionally:

- `check_transition` gains the theorem `Σ output values (+ retained escrows) at
  H_a == total_supply at H_a − 1` — supply conservation ACROSS the model change,
  in `sov-verify` where the existing conservation theorems live
  (`verify/src/invariants.rs:295+`).
- A conversion KAT: a pinned fixture ledger → pinned post-conversion root, in
  `sov-katgen`, mirrored in the TS SDK.

### 3.3 Activation discipline

- BIP-9 bit 3, baked preset via `baked_deployments()` (the F2 lesson from
  `notes/activation-v0198.md`: every parameter of the transition — H window,
  thresholds, any grace G — bakes into ONE preset; two nodes with different
  parameters split deterministically).
- **F6 boot-order invariant**: the conversion rule installs in
  `genesis_chain_with_baked_preset` BEFORE any replay tier, or a cold replay of
  a post-H_a log fails exactly like the v0.1.99 blocker. v0.3.0 additionally
  closes F6's open half with a mechanical test (deny-list bare
  `Blockchain::new` outside the constructor + tests) — see §10 W-F6.
- **Version contract** (`notes/release-version-contract.md`): one version
  source, tag == `node/Cargo.toml`, release only from `origin/main` head,
  artifact proves its version before staging. A ledger fork adds one clause:
  the release that ARMS bit 3 must refuse to build if the conversion KAT is
  absent or stale (release-gate extension).
- Mempool at the boundary: account-model txs admitted but unmined at `H_a`
  are dropped (their STF no longer exists); wallets are warned via RPC ahead of
  H_a (chain-state-driven, per F8's "notice served over RPC" clause).

### 3.4 The honest cost: both execution models, forever

A node syncing from genesis must execute the account STF for heights
`1..H_a − 1` and the UTXO STF thereafter. **Forever.** That means:

- `execution.rs` (6,463 lines) is never deleted — it is frozen as the
  historical engine, plus a second engine beside it. Both stay in the audit
  surface; both stay in the KAT surface (`stf.json` pins pre-H_a semantics;
  a new `stf-utxo.json` pins post).
- Every future global invariant (supply cap, per-asset conservation) must hold
  across the seam, and every future test that replays mainnet history exercises
  both engines.
- The only escape is checkpoint-style trust: bake a post-H_a state snapshot and
  make pre-H_a execution skippable (Bitcoin's `assumeutxo` is the precedent —
  external fact, high confidence). SOV already carries `assumevalid`
  checkpoints (PoW-skip only — sigs/roots still verified,
  `blockchain.rs:1618-1626`), and the memory of the v0.1.95 F1 finding
  (ancestry-gating) says extending trust from "skip PoW" to "skip execution"
  must be designed very carefully. Even with assumeutxo, the code both engines
  remains for anyone electing full verification — F8's spirit demands that
  election stay possible.

There is no design in which this cost is zero. Any pitch that omits it is
selling something.

## 5. F8 COMPLIANCE — value never stranded (adversarial-audit grade)

Law F8 (`notes/v0.2.0-program.md:164-201`): value consensus has accepted is
never made permanently unspendable; restriction only via its own deployment,
exit proven before restriction, spend-only before freeze, notice in blocks,
no unreachable value ever, old notes outlive upgrades unconditionally.

### 5.1 Account balances (Option A)

- **Keyed accounts** (implicit or named-with-key): converted to `Lock::Key /
  KeyAfter` outputs whose key hash equals the hash of the exact `PublicKey`
  already on the account. The SAME seed phrase signs; no wallet migration action
  is required before H_a; a wallet asleep for years wakes up owning outputs it
  can derive from §3.1's public rule. **Guaranteed**, provable by a
  `account-balance-never-stranded` e2e-vm test (sibling of
  `shielded-v1-never-stranded`, same SIGKILL/cold-replay/spend-after choreography).
- **Vesting locked balances**: `KeyAfter{unlock_height}` preserves both the
  value and the lock schedule exactly. **Guaranteed.**
- **Keyless IMPLICIT accounts** (mining payouts to fresh ids): the id IS the
  key hash; `Lock::Key(id)` is spendable by the preimage key exactly as today's
  self-certifying claim rule (`execution.rs:207-211`). **Guaranteed.**

### 5.2 Shielded notes v1 AND v2 (both options)

Notes live in commitment trees whose contents, nullifier sets, anchors,
turnstiles, and drain limiters are not touched by either option (verified: the
only coupling is the carrier's transparent leg, one code site,
`execution.rs:577-658`). Under Option A the carrier format changes; the note
itself, its witness path, and its spend proof do not. Required proof, both
options: extend `shielded-v1-never-stranded` to shield BEFORE the
ledger-model activation and spend AFTER it under the new carrier (and the v2
sibling once W2 exists). F8 clause 6 ("old notes outlive upgrades, including
cold replay from blocks.log") is the acceptance test verbatim. **Guaranteed
conditional on the carrier-leg port being in scope — it is (W-A4/§10), and the
arming release is gated on this test being green.**

### 5.3 The cases that canNOT be blanket-guaranteed (stated, not softened)

1. **Keyless NAMED accounts holding value** (e.g. value sent to an unclaimed
   `.sov` name; also the designed-keyless `xusd.reserve.sov` issuer). Today
   their claim path is `RotateKey` under rules we did NOT fully verify in this
   research pass (OPEN ITEM: exactly who may claim a keyless named account —
   the conversion rule cannot be written until that is pinned; memory says
   named value-accounts must be genesis-bound, which if enforced makes this set
   small). Mitigation: `Lock::Thread{NamedClaim}` preserves whatever today's
   claim semantics are, bit-for-bit, into the UTXO era — the value is not
   stranded, it is exactly as claimable as it was. What cannot be guaranteed is
   that "exactly as claimable" is *well-defined* until the claim rule is pinned.
   **Blocker-classed design prerequisite for Option A; a nonexistent problem
   for Option B** (the accounts persist).
2. **Vault debt positions**: converting `Vault{collateral, debt}` mints a
   Thread output — the value is preserved, but the OWNER's obligations move to
   a new interaction model; a vault owner using an old wallet cannot service
   the vault until tooling ships. Not stranding (F8's letter) but a freeze-like
   UX (F8's spirit). Mitigation: wallet/CLI vault support is an ARMING
   precondition (exit proven before restriction, F8 clause 2), not a
   post-activation follow-up.
3. **In-flight mempool txs at H_a** (§3.3): dropped, never stranded — funds
   untouched, resubmission required. Disclosed in release notes + RPC notice.
4. **Option B**: no conversion event exists; no case in this class arises.
   The one F8-relevant addition is the account⇄UTXO turnstile itself, which is
   spend-open in both directions from birth (§6.3) — verified as the same
   pattern the pools already satisfy.

## 6. OPTION B — THE HYBRID: UTXO WITH the account model (first-class design)

### 6.1 The observation to start from

SOV already runs Zcash's architecture: a transparent stateful layer plus TWO
note-commitment pools with consensus turnstiles and drain limiters (§0). Zcash
itself is precisely "a Bitcoin UTXO layer + shielded note pools + per-pool
value accounting that may never go negative" (external, high confidence: Zebra
RFC-0012 value pools; ECC turnstile enforcement). The hybrid option is
therefore NOT bolting a foreign model onto SOV — it is adding one more pool,
whose notes happen to be *transparent*, next to two that already exist, using
the identical, already-audited discipline:

```
                 ┌────────────── turnstile (shielded_value) ──── Orchard pool v1
account layer ───┼────────────── turnstile (v2, planned D11) ─── PQ pool v2
                 └────────────── turnstile (utxo_value, NEW) ─── transparent UTXO layer
```

### 6.2 Pinned design decisions (so nothing is relitigated mid-build)

| # | decision | value |
|---|---|---|
| D-H1 | UTXO tx envelope | A NEW top-level, nonce-free envelope `SignedUtxoTransaction` (§2.3 format, §2.4 sighash) admitted to blocks beside `SignedTransaction` post-activation. NOT a carrier Action — riding inside an account tx would inherit the nonce chain and deliver zero ordering win. Block body becomes `(Vec<SignedTransaction>, Vec<SignedUtxoTransaction>)` via an appended, absent-when-empty field so pre-activation blocks stay byte-identical. |
| D-H2 | Boundary actions | Account→UTXO: `Action::UtxoDeposit { outputs }` (appended tag 31; debits `signer.balance`, mints outputs, `utxo_value += Σ`). UTXO→account: an output `Lock::AccountCredit(AccountId)` which block-connect redeems into the account's balance (`utxo_value −= value`); credits need no nonce, so no recipient interaction. Deposit is an account action (it spends account balance and belongs under account rules); withdrawal is a UTXO output (it spends outputs and belongs under UTXO rules). |
| D-H3 | Scope of the layer at ship | XUS ONLY. No tokens, no NFTs, no datums, no Thread locks in v0.3.0. Lock set at ship: `Key`, `MultiKey`, `KeyAfter`, `Htlc`. Everything identity/stateful stays on accounts (that is the point of the hybrid). Extensions ride later deployments. |
| D-H4 | Turnstile | `utxo_value: Balance` scalar, reserved slot `sov:utxo_value`, `checked_add`/`checked_sub` (clone of `ledger.rs:1015-1031`); counted in `total_supply()` exactly like `shielded_value`/`htlc_locked`/`vault_collateral`. Consensus rejects any block driving it negative — same theorem family as Zcash value pools. NO drain limiter in either direction (both sides are transparent; the limiter exists on the shielded pools to bound counterfeit-under-proof-break, a threat that does not exist here — value is auditable by sum on both sides). |
| D-H5 | Commitment | UTXO set in the existing SMT, slot `blake3(0x08 ‖ borsh(outpoint))`, leaf `borsh(Output)`, absent-when-empty ⇒ genesis and all pre-activation roots byte-identical. Inclusion AND exclusion proofs come free (`smt.rs:77-107`). |
| D-H6 | Signatures | Hybrid Ed25519+ML-DSA-65 conjunction on BOTH layers, witness-dedup per distinct key (§2.3), Bound-only domain framing from birth (§2.4). Non-negotiable. |
| D-H7 | Reorg | New `UndoOp` variants: `UtxoCreate(Outpoint)`, `UtxoSpend(Outpoint, Box<Output>)`, `UtxoValue(Balance)` — three more of the existing 20; O(depth ≤ 256) reorgs preserved. Reorged UTXO txs re-enter the pool by input-conflict check (no nonce stranding possible on this lane). |
| D-H8 | Coinbase | UNCHANGED (credits the miner's account, `execution.rs:2061-2080`). UTXO-lane fees (Σin−Σout) are ALSO credited to the miner's account at block connect — one aggregation point keeps `check_transition` supply theorems single-seamed. Miners wanting outputs deposit explicitly. Revisit-later: coinbase-to-outputs as its own deployment. |
| D-H9 | Activation | One BIP-9 deployment, **bit 3**, LOT=false, thresholds/periods per house style; DEFINED in v0.3.0, ARMED by a later 2-line release after external audit (identical ladder to D13/bit 2). Pre-activation: `UtxoDeposit` ⇒ `FeatureInactive`; any block carrying a UTXO-lane tx or the new body field ⇒ invalid. Dormant chains byte-identical, proven by replaying the real mainnet log. |
| D-H10 | Per-lane mempool budget | The UTXO lane gets its own capacity slice and cluster limits (Core-31-shaped, sized by OUR weights — open measurement); the account lane keeps `(capacity/64).max(16)` unchanged. One shared feerate auction orders both lanes into the template (one price for blockspace — no fee-market split). |

### 6.3 Conservation across the boundary — reusing the proven pattern

The turnstile theorem extends `check_transition` exactly the way
`shielded_value` already participates in `total_supply` (`ledger.rs:972-984`):

```
supply_after == supply_before + Δmined
where supply = Σ accounts + shielded_value + htlc_locked + vault_collateral
             + utxo_value                                   // NEW term
and   utxo_value == Σ value over the committed UTXO set     // NEW theorem,
                                                            // checked per block
```

The second theorem (scalar == set sum) is what Zcash's per-pool balance rule
enforces and what SOV's redteam `check_ledger` sweep can assert per block; it
makes a bug in EITHER lane's execution arithmetically incapable of minting —
the same "supply survives a subsystem break" property the quantum-posture doc
claims for the pools (`chain/docs/quantum-posture.md`, turnstile section).

### 6.4 The mempool with both models present

- Two admission lanes, one price. Account lane: byte-identical logic to today
  (nonce runs, per-sender cap, affordability). UTXO lane: input-conflict sets,
  per-input existence check against tip state + in-pool spends, cluster
  limits, RBF by feerate-with-bump over conflicting input sets.
- One template auction: `select()` merges account nonce-packages and UTXO
  ancestor-packages by effective feerate/tip; the existing tie-break discipline
  (deterministic, lowest-id) extends with a lane tag. With zero UTXO txs the
  output is byte-identical to today's (the `no_tips_select_is_byte_identical…`
  test pattern, `lib.rs:1703-1745`, gets a sibling).
- Eviction floor: one pool-wide floor across both lanes (lowest
  feerate-per-weight victim regardless of lane) — otherwise the floor is
  gameable by lane-hopping.
- Persistence: `mempool.dat` gains a second section; restore re-validates each
  lane by its own rules (dropped-if-stale semantics unchanged).

### 6.5 What the hybrid does NOT need

No snapshot conversion. No dual execution engines. No account deletion. No
KAT regeneration (only ADDITIVE new vector families). No wallet forced
migration. No F8 conversion analysis (§5.3 case 4). The existing chain history
replays byte-identically because everything is appended and absent-when-empty —
the same additive-dormant discipline as every SOV fork to date.

### 6.6 What each layer is FOR (and the user-facing rule)

- **Accounts** (identity + evolving state): xUSD vaults, names/SNS, multisig
  policies, tokens+compliance, contracts, oracle — everything that needs
  durable identity or in-place mutation.
- **UTXO** (bearer cash): plain XUS transfers at volume, treasury/reserve
  tranching (multi-key, timelocked, independently-keyed outputs), payment
  privacy-by-default (fresh lock per output), HTLC legs, and any flow that must
  never be blocked by an unrelated pending tx.
- **The wallet rule** (stated because if it isn't obvious it's a cost):
  *"Identity lives on your account; cash lives in your outputs."* Default send
  path for plain XUS = UTXO lane once active; account balance is what vaults,
  names, and tokens operate on; Station shows FOUR buckets (transparent
  account / cash-UTXO / shielded v1 / shielded v2) with one-click movement
  through the turnstiles. This is real UX surface and real user education —
  priced in §6.7, not hidden. (Precedent: Zcash wallets have shipped exactly
  this transparent/shielded split for years; it is workable, not free.)

### 6.7 Honest costs of the hybrid (it is not free)

1. **Two of everything, permanently**: two validation paths, two mempool
   lanes, two wallet code paths, two SDK surfaces, two explorer views, double
   the ongoing audit surface. The protocol is permanently more complex than
   either pure model.
2. **UX fragmentation**: users hold value in up to four places with different
   properties; support burden and footgun surface grow accordingly.
3. **Liquidity/anonymity split**: transparent-UTXO privacy improves only with
   adoption of fresh-lock discipline; value split across layers thins each
   layer's crowd. (Same disclosed trade-off as dual shielded pools, D12.)
4. **The boundary is consensus surface**: the turnstile, `AccountCredit`
   redemption, and dual-lane block validity are new rules that can fork the
   chain if wrong — smaller than Option A's surface by an order of magnitude,
   but not zero.
5. **It does not deliver** UTXO-native vaults/names/contracts — by design. If
   the owner's end-state is a pure-UTXO chain, the hybrid is a (credible,
   de-risking) waypoint, not the destination.

### 6.8 Prior art for the hybrid, concretely

- **Zcash**: transparent + shielded pools, per-pool chain value balances that
  consensus forbids from going negative (Zebra RFC-0012; ZIP-209 lineage), and
  turnstile-enforced migrations (Sprout→Sapling). SOV's own pools already copy
  this; the hybrid extends it by one pool. Confidence: HIGH.
- **Qtum**: a UTXO base ledger with an account-model EVM on top, bridged by the
  Account Abstraction Layer (OP_CREATE/OP_CALL/OP_SPEND, later OP_SENDER,
  QIP-5) — proof that a production chain can run both models against one supply
  for years. Its direction is inverted from ours (UTXO-primary), which is
  itself informative: BOTH orientations work; the bridge is the design load.
  Confidence: HIGH on architecture, MEDIUM on operational details.
- **Nervos CKB**: generalized-UTXO base (cells, lock/type scripts) with
  account-model layers built above — the "each layer where it's strong"
  argument made explicit in their RFCs. Confidence: HIGH.
- **Cardano eUTXO**: what full migration would require for stateful features,
  and the documented concurrency cost of state-threads (WTSC'20 paper;
  reference inputs added later in CIP-31). Confidence: HIGH.
- **Ethereum**: the account model's own answer to ordering pain is queued
  future nonces + replacement pricing — client policy, not protocol (see §7.1).
  Confidence: HIGH.

## 7. OPTION C — LOWER-COST ALTERNATIVES (fair hearing, decision-record grade)

### 7.1 Ethereum-style queued future nonces

Admit nonce-gapped txs into a non-mineable "future" tier; promote when the gap
fills. Cost: mempool-only change (~admission + promotion logic + eviction
tuning), zero consensus surface, zero KAT impact. Benefit: submission UX
(clients can fire-and-forget out of order). **What it does NOT fix**: mining
order — the STF's strict `tx.nonce == signer.nonce` makes mining over a gap
impossible by definition, so head-of-line blocking at selection remains
(`select_never_proposes_a_gap_tx` stays true). It also reopens the stranding
DoS the gap-free rule was built to prevent (the mempool's own doc comment,
`lib.rs:12-14`, records that lesson). Verdict: cheap, small real UX win, does
not touch the owner's stated goal.

### 7.2 Raise the per-sender cap (256 → more)

One constant (`default_per_sender`). But the number is already 10× Bitcoin's
historical ancestor limit and 4× Core 31's cluster size; no evidence in this
tree or the notes of the cap binding in practice (OPEN MEASUREMENT: mainnet
mempool occupancy/eviction telemetry). Verdict: a non-solution to a problem we
have not measured having.

### 7.3 Access-list parallel execution

Declare read/write sets per tx (EIP-2930-shaped), execute disjoint txs
concurrently at import. Node-local performance only; no consensus change if
schedules stay deterministic; does nothing for ordering or privacy. Honest
blocker: we have NO measurement showing state application (as opposed to
signature verification, already parallelizable) is a bottleneck — §12. Verdict:
premature optimization until measured.

### 7.4 Let the shielded pools carry the load

The pools ARE note ledgers with independent ordering today. A user wanting
unblocked parallel spends can shield and z-send now (mainnet-proven lifecycle,
`notes/` 2026-07-23). Costs: proof latency (~21 ms v2 prove is fine; Orchard
heavier), 40 KB v2 carriers, drain-limiter caps on exit (21,000 XUS/576
blocks), HNDL disclosure on v1 — and every pool carrier tx is itself an
account-nonce tx, so the transparent boundary still serializes per signer.
Verdict: real partial relief, wrong tool for transparent treasury flows.

### 7.5 Why none of these is the answer to the brief

C-options deliver: fee market (already have), submission UX (7.1), node perf
(7.3). None delivers independent ordering of transparent value, bearer
outputs, or receiver-side coin control. If those are the goals — and the
owner's decision says they are — the honest menu is Option A or Option B.

## 9. RECOMMENDATION

**Ship v0.3.0 as the HYBRID (Option B), scoped per §6.2, sequenced after
v0.2.0's W2; treat it explicitly as a de-risking waypoint that keeps full
migration (Option A) open; adopt 7.1 (queued future nonces) as a cheap
independent mempool improvement; fix D4's nonce binding NOW, before W2 lands.**

Reasoning, in the open:

1. **The hybrid delivers the owner's actual goals** — independent ordering,
   bearer outputs, coin control, privacy defaults, under the existing fee
   market — for every flow that wants them, without betting the chain on a
   one-shot conversion.
2. **The full migration converges to a hybrid anyway** (§2.6): velocity
   windows, the oracle, and contracts each force either feature loss or an
   identity sidecar. If "full" honestly means "UTXO plus an account-shaped
   sidecar," then choosing the hybrid is not a retreat from the decision — it
   is the same end-state reached without the stranding event.
3. **F8 arithmetic**: Option A's §5.3 list is real and one item (keyless named
   accounts) is a design blocker with an unpinned dependency. Option B's F8
   section is one paragraph because no value moves involuntarily. For a chain
   whose bar is "state reserve-asset grade," that asymmetry should dominate.
4. **It is the pattern this codebase is best at**: additive, dormant,
   absent-when-empty, turnstiled, BIP-9-armed later — executed successfully
   four times (tx-domain, fee-auction, pools v1/v2-in-flight). Option A has no
   precedent in this tree; Option B has four.
5. **Full migration stays live**: if after a year of the cash lane the owner
   wants accounts gone, the lane IS the destination ledger — migration becomes
   "everyone walks through an existing, battle-tested turnstile under an F8
   schedule," i.e. Zcash-style pool retirement of the *account* side, with the
   conversion of §3 shrunk to the stragglers. That path is strictly safer than
   converting cold.

If the owner overrules and mandates Option A regardless: this document's §§2–5
are the executable plan; the DECISION-NOW items and W-F6 below apply
unchanged; and the arming release must be gated on §5's three never-stranded
tests plus a pinned resolution of §5.3.1.
