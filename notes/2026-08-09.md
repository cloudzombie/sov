### §3A.3 — `xust1…` checksummed transparent addresses (`chain/crates/shielded/src/address.rs`)

- New presentation-layer encoding for IMPLICIT (64-hex) transparent account ids: the 32-byte id
  under the SAME bech32m engine (`Bech32mLong`) the shielded tiers use, HRP `xust`. Named
  accounts have no `xust1…` form (`encode_transparent` → `None`) — a name is not a 32-byte id.
- `decode_transparent` yields the IDENTICAL raw-hex `AccountId`; `AnyAddress::parse` accepts the
  new spelling, so `RpcClient::pay`, `sov-wallet transfer`, and Station all take it with no
  further changes. Raw 64-hex stays accepted forever.
- **Zero-consensus-surface proof**: `chain/crates/wallet/tests/transparent_checksum.rs` pins that
  a signed transfer built from an `xust1…` recipient is BYTE-IDENTICAL (borsh consensus bytes,
  JSON-RPC submission payload, and tx id) to one built from raw hex. Signing is deterministic
  (Ed25519 + ML-DSA FIPS-204 deterministic mode), so full-envelope equality holds.
- Test bar mirrors the pool-v2 suite: every single-character substitution at every position
  rejected; every deletion, charset insertions at every position, and every adjacent
  transposition rejected; `decode(encode(id)) == id` over a corpus; canonical lowercase;
  uppercase decodes (bech32m case rule).
- `SHIELDED_V2_ADDRESS_CHARS` (= 1957) + `shielded_v2_looks_truncated` classify a clipped
  `xusq1…` paste as TRUNCATED distinctly from a checksum failure.

## Deliberately NOT done — §2.2 (the four `#[ignore]`d sync tests stay ignored)

Verdict after inspection: these cannot be made deterministic without refactoring live sync code,
and that refactor does not belong in the release that must not break anything.

- `SyncState::{request_missing, handle, collect_verify_reports}` take a concrete `&TcpNode` —
  there is NO transport abstraction to substitute an in-memory deterministic transport for the
  real encrypted (Noise + ML-KEM) loopback sockets.
- Wall-clock `Instant::now()` is read at ~20 sites inside the sync engine (inflight deadlines,
  strike escalation, status TTLs, announce cadence). An injected clock means threading a time
  source through the exact strike/deadline logic that PR#39 fixed — a behavior-risk change to
  the most incident-prone code in the tree, for test convenience.
- The third fork-recovery test additionally depends on a real 16 s outage window against the
  real escalating request deadlines (2+4+8 s) — inherently wall-clock as written.

Per the release spec's own rule ("a flaky test that reds releases is worse than an ignored
one"), all four stay `#[ignore]`d and runnable on demand via `--ignored`. The honest path to
§2.2 is a v0.2.12+ change: introduce a transport trait + injectable clock in `SyncState` as its
own reviewed slice, then de-ignore. Note §6.4 of the release notes ("the ignored sync tests
run") is therefore NOT satisfied by this slice — flagged for the owner's release decision.
