## 2026-07-31 — v0.2.8: the self-fork pair

Two P2P fixes that together close the mainnet fork-poisoning incident (the "won't sync past
~256" / endless fork-point thrash that destroyed sgp1 and forked the Windows box). They are
deliberately paired: one fixes fork **recovery**, the other fork **creation**.

### `7b3956d` (PR #39) — sync-strike deadlock: fork RECOVERY

A node on its own divergent fork could **never** reorg onto the heavier canonical chain if its
honest peer was briefly slow. Three unanswered block requests (`BLOCK_REQUEST_TIMEOUT` = 2 s)
hit `STATUS_MAX_STRIKES`; `status_actionable()` then disqualified that peer from catch-up
selection **forever**, because strikes were only cleared in `advance_or_done()`, which only runs
for a peer that gets *selected* — and a disqualified peer is never selected again. End state: a
resolved fork point, a live honest peer answering every request, and no peer the node was
willing to sync from.

Fix: a **delivered** reply substantiates the peer's advertised chain, so a non-empty
`BlocksResponse`, a backtrack `BlockResponse(Some)`, or a valid attached `Headers` reply clears
that peer's stall strikes. A peer that advertises a tall chain and never delivers still accrues
strikes and stays disqualified — the invariant the counter exists for. Garbage replies are still
penalized via `Invalid`. Fork choice, orphan rejection, checkpoint linkage and PoW unchanged.

Pinned by `divergent_fork_node_with_fork_peer_recovers_honest_peer_after_transient_stall`
(real `Blockchain` + `SyncState` + `TcpNode` loopback, `--ignored`): the exact incident shape —
A on its own 256-block fork, fork-serving peer C at 260, honest B at 300 that misses three
requests then answers forever. Deterministically wedged at 260 on the old code; converges to B.

### `b3c002c` (PR #40) — peerless solo-mining: fork CREATION

The root cause of the self-forks. Once the startup grace lapsed, a node with **zero peers** fell
through to `MinePhase::Mining` and began "solo/seed bootstrap" mining thousands of blocks below
the real tip — forking itself off mainnet. Peer loss at a 256-batch seam during sync was the
trigger.

Fix: `decide_mine_phase()` extracted, and it **fails closed on a checkpointed chain** — zero
peers, unknown peer height, or an unmatched newest checkpoint ⇒ wait/sync, never mine. An
*un*-checkpointed chain (dev/test/seed bootstrap) keeps the old grace-then-solo-mine behavior, so
standing up a brand-new network is unchanged. Also: catch-up now falls back to a struck-out peer
rather than going idle, and request timeouts escalate with strikes, capped.

Verified independently: 7 mining-gate tests + the fresh-node-across-batch-boundaries integration
test; the old code demonstrably solo-mines past grace.

## 2026-08-01 → 08-02 — v0.2.9: light mode, per-wallet pools, honest confirmations

### `b2f3a61` — RandomX light mode on low-RAM hosts (the droplet OOM)

`seal.rs`'s claimed "small VPS falls back to light" **never fired on Linux**: the `FLAG_FULL_MEM`
dataset allocation overcommits, so the OOM killer `SIGKILL`s the process mid-population and the
`Ok`/`Err` fallback is unreachable. This is what broke sfo3.

Fix: `host_has_ram_for_fast_dataset()` reads `/proc/meminfo` `MemAvailable` and demotes to light
mode **proactively** under ~2.6 GiB; non-Linux (dev) keeps the fast path. RandomX guarantees
fast and light produce **identical** hashes (proven by the `randomx_mining_and_verify_paths_agree`
ignored test), so a light miner still finds valid blocks. Purely local, performance-only, never
consensus-affecting. 15 pow tests + the 2 GiB equivalence test pass.

> Ops consequence: the two surviving droplets are 1.9 GiB, i.e. **under** RandomX's ~4 GiB. From
> v0.2.9 they self-demote. Do not deploy a pre-0.2.9 build to them expecting it to fit.

### `8081a6b` — per-wallet shielded pool views

The Station held **one global slot** per pool (`shielded: Arc<Mutex<ShieldedView>>`,
`shielded_v2: …`). Every scan overwrote it, so scanning wallet B destroyed wallet A's view —
"I can only view one wallet's v2 pool at a time." Only a hand-written `view.account == account`
check repeated at each paint site kept A's figures off B's screen.

Fix: both slots become `ScannedPools<V>`, keyed by the wallet the scan was run **for**. The key is
`LoadedWallet::scan_key` — the wallet's own implicit account id, the fingerprint of the key that
can actually decrypt those notes. Not the display label (renameable) and not `effective_account()`
(linking/unlinking a named account changes who *signs*, never which notes the seed controls; the
old code mixed the two). Unscanned stays **unknown, never zero**; a wallet scanned and found empty
still reports a real, distinguishable zero. `ShieldedV2View::guard()` zeroes notes and balance for
a foreign view, so cross-wallet isolation is now structural.

### `035e527` — a pending pool-v2 tx is NOT a failure

`submit_v2_bundle` waited 120 s for a receipt and returned `Err` on timeout; `run_v2_action`
rendered any `Err` as `"{noun} failed: {e}"`. So a shield sitting safely in the mempool displayed
as `shield failed: still pending (not yet mined)` — self-contradictory, and **dangerous**: it
tells an operator their value did not move while the tx is live, and the obvious response
(resend) spends a **second nonce** on an action already in flight. A ~11 KiB v2 bundle routinely
misses a 120 s window.

Now modelled honestly: `ReceiptStatus::{Confirmed, Pending, Rejected(reason)}`, and an `Err` from
`submit_v2_bundle` means **never broadcast** (no nonce used, retry is correct). `await_receipt_status()`
yields `Pending` on timeout — only a receipt may declare failure. Pool-v2 actions now register a
`SentTx` in the **outbox**, tracked to a terminal state by the same receipt poller as transparent
sends; previously, past the inline wait Station simply forgot the tx existed, which is why there
were no actual v2 confirmations. Inline wait cut 120 s → 45 s. Wording extracted to pure
`v2_status_line()` / `v2_not_broadcast_line()` so the rule is **tested, not trusted** (4 regression
tests).

## 2026-08-02 — v0.2.10: the three defects the usability pass surfaced

`68e3773` (PR #49):

1. **Affordability.** `V2Intent::Shield` validated the amount only against itself, so a shield
   larger than the wallet's transparent balance passed every local guard and was refused by the
   **node** — after ~25 s of STARK proving. `V2Guard` gains `transparent_grains` and the `Shield`
   arm refuses up front, naming the real constraint. `None` (unknown) is **not** treated as zero:
   an absent reading authorises nothing extra but never manufactures a refusal, matching how an
   unscanned pool balance is handled.
2. **Double-fire.** Amount fields were never cleared after a successful shield / de-shield /
   private send, so a second click re-fired the **same amount** at an action already in flight.
   `run_v2_action` (and its three wrappers) now report whether a worker was actually spawned, and
   the caller clears the amount **only on a real dispatch** — a validation refusal leaves what was
   typed intact instead of eating it.
3. **Silent overwrite.** "Shield to my pool" replaced a pasted recipient with no way back. The
   prior value is kept with an inline **Undo**; typing in the field drops the stale undo so it can
   never overwrite a recipient just asserted.

3 tests pin the affordability rule (over-balance refused, unknown never refuses, bound applies to
shield only — pool spends stay bounded by notes and the de-shield window). Suite 133 passed / 0
failed, fmt + clippy clean.

Tag `v0.2.10` = `eb51cd6`, release-gate green.

## 2026-08-02 — `9eee9d9`: anchor → 15872, and the refresh script was broken

**The gate correctly refused to cut v0.2.10.** The baked anchor was 14336 against a live tip of
16569 — lag 2233, over the `CP_MAX_LAG` of 2000 (`scripts/release-gate.sh:190`). This is the A1
guard from `consensus-open-list.md` doing exactly its job.

New anchor **15872** = `c5ce1b62…4bc1`, ~698 deep (far past finality). Cross-checked **identical
on two independent relays over two transports**: sfo3 via public RPC, fra1 via SSH to its loopback
RPC.

**Why it had to be done by hand — and the real lesson.** `scripts/refresh-checkpoint.sh` was
broken by sgp1's removal: its relay list still named the destroyed droplet, and under
`set -euo pipefail` curl's exit 7 aborted the whole script. **The refresh failed silently and the
anchor rotted until the gate caught it.** Fixed: dead relay dropped, an unreachable relay is now
an ordinary outcome (`|| true`) rather than fatal, and it is documented that fra1 binds RPC to
loopback — so **only one relay answers publicly, and the two-confirmation rule must be completed
by hand until a second public relay exists**.

Weak-subjectivity anchor: genesis-safe and additive. A chain reaching 15872 with a different hash
is still rejected by the hash pin.
